# Tunnel Panel — راهنمای فارسی

یک پنل تک‌باینری (به‌همراه ربات تلگرام) که روی **سرور خارج (رله)** نصب می‌شود و آن را به یک یا چند
**سرور ایران** وصل می‌کند. شما یک «تونل» می‌سازید (یک مسیر: سرور ایران ⇄ سرور خارج + چند پورت)،
یک **روش اتصال** انتخاب می‌کنید و هر وقت خواستید بین روش‌ها جابه‌جا می‌شوید. پنل خودش کانفیگ و
سرویس‌های systemd را روی **هر دو** سرور می‌نویسد، پورت‌های عمومی ایران را به سمت خارج فوروارد می‌کند،
و حتی وقتی SSH ایران بسته باشد هم می‌تواند به آن برسد.

> نسخهٔ انگلیسی: [README.md](README.md) — تحلیل فنی همهٔ پروژه‌های پایه در پوشهٔ [docs/](docs).

## نصب سریع

روی **سرور خارج** و با کاربر root:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/aliasgari-ka/tunnel-panel/main/install.sh)
```

این دستور وابستگی‌ها را نصب می‌کند، اگر Go نبود خودش نصبش می‌کند، باینری را می‌سازد، یک سرویس
systemd می‌سازد و آدرس پنل را چاپ می‌کند. اولین بار که `http://<ip-خارج>:8088/` را باز کنید،
حساب ادمین را می‌سازید.

گزینه‌ها:
- `--port 8088` پورت پنل، `--agent-port 7020` پورت اتصال agentهای ایران.
- `--domain panel.example.com` → پنل خودش از Let's Encrypt گواهی SSL می‌گیرد و روی **HTTPS** (پورت ۴۴۳) بالا می‌آید. دامنه باید به IP همین سرور اشاره کند و پورت‌های ۸۰ و ۴۴۳ باز باشند.
- `--ip-ssl` → گواهی **معتبر و بدون هشدار** برای خودِ IP سرور، از طریق sslip.io. پنل روی
  `https://<ip-با-خط-تیره>.sslip.io` بالا می‌آید (پورت‌های ۸۰ و ۴۴۳ باید باز باشند، دامنه لازم نیست).
- `--self-signed` → HTTPS با گواهی self-signed (مرورگر یک بار هشدار می‌دهد). برای وقتی ۸۰/۴۴۳ باز نیست.
- بدون این‌ها → HTTP ساده.

## مفاهیم پایه

- **سرور ایران (iran):** نقطهٔ ورود کاربران. کاربر به IP ایران و پورت موردنظر وصل می‌شود.
- **سرور خارج (foreign):** جایی که سرویس واقعی آن‌جاست؛ پنل هم روی یکی از همین‌ها نصب است.
- **تونل:** یک مسیر بین یک سرور ایران و یک سرور خارج، با یک یا چند پورت.
- **روش (method):** تکنیکی که تونل با آن برقرار می‌شود (Backhaul، GRE، IPsec، …). قابل تعویض است.
- **agent:** یک باینری کوچک که روی سرور ایران اجرا می‌شود و **از ایران به سمت پنل** وصل می‌شود؛
  برای وقتی که سرور ایران SSH ورودی ندارد.

هر تونل یک شمارهٔ یکتا (index) می‌گیرد؛ از روی آن یک زیرشبکهٔ خصوصی (`10.10.N.0/30`) و نام رابط و
پورت‌های داخلی ساخته می‌شود تا تونل‌ها هیچ‌وقت با هم تداخل نکنند.

## روش‌های اتصال

| روش | خانواده | رمزنگاری | توضیح |
|---|---|---|---|
| **BackPack reverse** | v4/v6 | stealth (Noise)/TLS/توکن | ایران listen، خارج dial. ۱۲ ترنسپورت از جمله `stealth`، `quic`، `wssmux` |
| **BackPack L3 (TUN)** | v4/v6 | Noise AEAD | این بار ایران به خارج وصل می‌شود؛ وقتی ایران پورت ورودی باز ندارد |
| **Backhaul reverse** | v4/v6 | توکن/wss | tcp، tcpmux، ws، wss، wsmux، wssmux، udp |
| **FRP reverse** | v4/v6 | توکن (+TLS) | tcp، websocket، quic، kcp |
| **Backhaul Premium** | v4 | AEAD (ipx)/TLS | `tun` با کپسوله‌سازی `ipx` (icmp/ipip/udp/tcp/gre/bip) و `anytls`. فقط amd64 |
| **Backhaul Premium v1 (legacy)** | v4/v6 | توکن/wss | هسته‌ی v1.0.2 فروشنده برای arm64، همراه پنل (WTFPL)؛ روی arm64 مستقیم و روی amd64 با qemu-aarch64؛ هر دو سرور v1 اجرا می‌کنند |
| **Golden-GRE** | v4 | اختیاری XChaCha20 | GRE داخل FOU با پوشش DNS یا ICMP؛ چند تانل می‌توانند پورت 53 یک سرور را با هم استفاده کنند |
| **Direct v6 (ip6gre)** | v6 | ندارد | فقط کرنل، کمترین سربار؛ Carrier روی `udp` یعنی GRE داخل UDP برای مسیرهایی که پروتکل 47 را می‌بندند |
| **Plain GRE** | v4/v6 | ندارد | GRE یا ip6gre کرنل |
| **IPsec (strongSwan)** | v6/v4 | AES-GCM | IKEv2، رابط XFRM مسیری |
| **Spoof-Tunnel** | v4 | ندارد (جعل IP) | پایپ خام با جعل متقابل IP مبدأ؛ provider نباید egress filtering داشته باشد؛ داخلش یک پروتکل رمزدار بگذارید |

## راه‌اندازی گام‌به‌گام

۱. **تنظیمات (Settings):** IPv4/IPv6 عمومی همین سرور خارج را وارد کنید. «Agent dial-back address»
   را هم بگذارید (مثلاً `203.0.113.5:7020`) تا دستور نصب agent درست ساخته شود.

۲. **سرورها (Servers):** سرور ایران را اضافه کنید (نقش = iran)، هر سرور خارجِ دیگر را با نقش foreign.
   یا رمز/کلید SSH بدهید، یا از **Agent install** استفاده کنید. دکمهٔ **Test paths** همهٔ مسیرها را
   چک می‌کند و می‌گوید کدام کار می‌کند و سرعتش چقدر است.

۳. **تونل‌ها (Tunnels):** روی **+ New tunnel**: سرور ایران + سرور خارج + خانواده (v4/v6) + پورت‌ها.
   سپس روی کارت تونل یک روش انتخاب کنید، با ⚙ تنظیمش کنید و **Start** بزنید. برای تغییر روش،
   روش دیگری انتخاب و **Switch** کنید؛ پنل اول روش قبلی را روی هر دو سرور جمع می‌کند. **Logs**
   لاگ زندهٔ هر دو سرور را نشان می‌دهد.

قالب پورت‌ها: `443` یا `8080=80` (ورودی ۸۰۸۰ → مقصد ۸۰) یا بازه `2000-2010`، با کاما جدا:
`443,8080=80,2000-2010`.

## وقتی SSH ایران کار نمی‌کند

پنل به‌ترتیب این مسیرها را خودکار امتحان می‌کند:

```
agent (برعکس)  →  SSH مستقیم  →  SSH از طریق پروکسی  →  SSH از طریق سرور دیگر (jump)
```

- **agent برعکس (بهترین):** روی سرور ایران دکمهٔ **Agent install** را بزنید و دستور یک‌خطی را آن‌جا
  اجرا کنید. یک باینری کوچک (`tp-agent`) از خود پنل دانلود می‌شود و از ایران به سمت پنل وصل می‌شود.
  دیگر هیچ پورت ورودی یا SSH روی ایران لازم نیست. کلید پنل pin می‌شود (ضد MITM).
- **jump:** اگر سرور دیگری به ایران می‌رسد، در تنظیمات سرور می‌توانید «Force jump via» را انتخاب کنید
  یا روی auto بگذارید تا خودش از هر سرور قابل‌دسترس به‌عنوان واسطه استفاده کند.
- **پروکسی:** برای هر سرور می‌توانید `socks5://user:pass@host:port` یا `http://host:port` بگذارید.
- **SSH bridge:** یک پورت روی پنل باز می‌کند که از بیرون به آن وصل شوید و خودش شما را به SSH ایران
  برساند — حتی وقتی ایران ورودی ندارد (دکمهٔ **SSH bridge** روی کارت سرور).

## پورت فوروارد و چند سروره

- **پورت فوروارد:** روی سمت ایران، پورت‌های عمومی با iptables به سمت خارج DNAT می‌شوند (به‌همراه
  MSS clamp). قوانین در زنجیره‌های جدا برای هر تونل هستند و موقع stop تمیز پاک می‌شوند. پورت SSH
  هیچ‌وقت فوروارد نمی‌شود تا قفل نشوید.
- **یک خارج ↔ چند ایران** یا **چند ایران ↔ یک خارج:** کافی است چند تونل بسازید؛ هر تونل جفت سرور
  خودش را دارد و با index یکتا جدا می‌شود، پس هیچ تداخلی پیش نمی‌آید.

## بنچمارک

در بخش **Benchmark** یک سرور ایران و یک سرور خارج انتخاب کنید و **Run** بزنید. پنل هر روشِ سازگار را
روی یک تونل موقت بالا می‌آورد، تأخیر/جیتر/افت بسته/سرعت را اندازه می‌گیرد، تونل را پاک می‌کند، و
بهترین را با امتیاز پیشنهاد می‌دهد. با یک کلیک می‌توانید بهترین روش را روی یک تونل واقعی اعمال کنید.

## بهینه‌سازی کرنل

روی کارت هر سرور دکمهٔ **Optimize**:
- سرور را تشخیص می‌دهد: نسخهٔ کرنل، نوع مجازی‌سازی، RAM، تعداد CPU، و پشتیبانی BBR.
- تنظیمات sysctl متناسب با همان سرور می‌سازد (BBR+fq اگر موجود بود، بافرها بر حسب RAM، `ip_forward`،
  `tcp_fastopen`، محدودیت فایل و …).
- **Apply now** خودش روی سرور اعمال می‌کند؛ اگر نشد، **دستور کامل root** را می‌دهد تا دستی اجرا کنید.
  این تنظیمات استاندارد و محافظه‌کارانه‌اند و SSH را قطع نمی‌کنند.

## شکل‌دهی ترافیک (Traffic shaping)

در فرم ساخت/ویرایش تونل، بخش «Traffic shaping / link tuning»:
- qdisc: `cake`، `htb`، `tbf` یا `fq_codel` (با fallback خودکار اگر کرنل یکی را نداشت).
- jitter (netem)، MSS clamp، انتخاب اینترفیس خروجی، و «روی سرور خارج هم اعمال شود».
- به‌صورت یک سرویس systemd جدا بعد از بالا آمدن تونل اجرا می‌شود و موقع stop پاک می‌شود. تغییر در
  Start/Switch بعدی اعمال می‌شود.

## خودکارسازی و عیب‌یابی

- **Failover خودکار:** اگر تانلی ۵ دقیقه قطع بماند، پنل روش دیگر یا خانواده‌ی دیگر (IPv4 ⇄ IPv6) را امتحان می‌کند و فقط وقتی نگه می‌دارد که یک اتصال واقعی از پورت فوروارد شده به سرویس روی سرور خارج برسد. هر ساعت مسیر اصلی (روی یک اسلات جدا، بدون قطع تانل) تست می‌شود و اگر سالم بود برمی‌گردد. برای هر تانل قابل خاموش کردن است.
- **گزارش قطعی (Outage log):** پورت SSH همه‌ی سرورها هر ۱۰ ثانیه چک می‌شود (هر خطا دو بار دیگر تکرار می‌شود، پس یک بسته‌ی گم‌شده قطعی حساب نمی‌شود ولی قطعی ۱۰ ثانیه‌ای ثبت می‌شود). هر قطعی سرور یا تانل با زمان دقیق شروع و پایان (به وقت تهران) در صفحه‌ی Servers و دکمه‌ی «📉 Outages» ربات نگه داشته می‌شود؛ برای تانل‌ها گفته می‌شود سرورها در آن لحظه جواب می‌دادند یا نه (مشکل از تانل است یا سرور)، و تلگرام هم موقع قطع و هم موقع وصل شدن خبر می‌دهد.
- **Diagnose:** همه‌ی مراحل را بررسی می‌کند و مشکل را با راه‌حل می‌گوید. اگر سرور ping را جواب ندهد ولی
  اتصال TCP از داخل تانل برقرار شود، تانل سالم حساب می‌شود (فقط یک ⚠ نشان داده می‌شود) — نه در Diagnose
  و نه در failover خطا حساب نمی‌شود.
- **Trace:** ۳۰ ثانیه کلاینت (مثلاً Xray) را وصل کنید؛ نشان می‌دهد اتصال کجا متوقف می‌شود و لاگ خود Xray را هم می‌آورد.
- **Speed test**، **ترافیک لحظه‌ای** و **تاریخچه‌ی بنچ‌مارک** (کدام سرور با کدام سرور، کی، و نتیجه).
- **قبل از تانل ریورس** بررسی می‌شود که سرور خارج به پورت ایران می‌رسد؛ اگر نه، پورتی که رد می‌شود (443، 8443، …) انتخاب می‌شود.

## ربات تلگرام

در **Settings** توکن بات و chat id ادمین را بگذارید. به بات `/start` بدهید؛ اگر هنوز ادمین نباشید،
chat id خودتان را جواب می‌دهد تا در تنظیمات واردش کنید. بات با دکمه همهٔ کارها را می‌کند:
فهرست تونل‌ها، start/stop/switch روش، و وضعیت. در «⇄ Method / IPv4·IPv6» اول خانواده‌ی آدرس
(IPv4 یا IPv6) را انتخاب می‌کنید و بعد روش را؛ روش‌هایی که فقط روی یکی کار می‌کنند (مثل Golden-GRE که فقط
IPv4 است) زیر همان خانواده نشان داده می‌شوند. با «⚙ Settings» تنظیمات روش هر تانل (مثلاً transport و پورت Backhaul) را از داخل ربات عوض می‌کنید و با «↻ Apply changes» اعمال می‌کنید. چون long-polling است، روی سروری که HTTP ورودی ندارد
هم کار می‌کند.

## باینری‌های کمکی

هستهٔ **Backhaul Premium** سورس‌بسته است و همراه پروژه نمی‌آید و از HTTP هم دانلود نمی‌شود. یک بار از
**Settings → Helper binaries** آپلودش کنید (با نام `backhaul_premium-amd64`)؛ پنل آن را نگه می‌دارد و
خودش سالم و با hash به سرورها می‌رساند. باینری‌های Backhaul/FRP/BackPack هنگام نیاز از ریلیزهای رسمی
گیت‌هاب گرفته می‌شوند (می‌توانید یک پیشوند mirror در تنظیمات بگذارید).

## امنیت

- برای HTTPS یا `--domain` (گواهی واقعی) یا `--self-signed` را به نصب‌کننده بدهید؛ در غیر این‌صورت
  پنل روی HTTP بالا می‌آید. می‌توانید پشت reverse proxy هم بگذاریدش.
- فایل حالت (`/etc/tunnel-panel/state.json`، مود 0600) شامل رمز/کلید SSH سرورهاست؛ آن سرور را حساس
  در نظر بگیرید.
- برای هر تونل یک توکن/PSK تصادفی ساخته می‌شود؛ از مقادیر پیش‌فرض عمومی ابزارهای پایه استفاده نمی‌شود.
- پنل برای لاگین rate-limit دارد، درخواست‌های حالت‌تغییردهنده را فقط با `application/json` می‌پذیرد
  (ضد CSRF)، و کلید agentها را pin می‌کند.
- **Spoof-Tunnel** رمزنگاری ندارد و فقط وقتی کار می‌کند که هر دو provider اجازهٔ ارسال بسته با IP جعلی
  بدهند؛ داخلش یک پروتکل رمزدار (مثل WireGuard) بگذارید.

## ساخت از سورس

```bash
bash build.sh amd64 arm64      # به Go و gcc نیاز دارد؛ خروجی در dist/tunnel-panel-<arch>
```

`build.sh` خودش `tp-agent` (هر دو معماری) و رلهٔ Golden-GRE (پوشهٔ `third_party/golden-gre`،
مجوز Apache-2.0) را می‌سازد و داخل باینری پنل جاسازی می‌کند.

## عیب‌یابی

- **تونل بالا نمی‌آید:** روی کارت تونل **Logs** را باز کنید؛ لاگ هر دو سمت (IR/KH) را می‌بینید.
- **سرور ایران unreachable:** روی کارت سرور **Test paths** را بزنید تا ببینید کدام مسیر کار می‌کند؛
  اگر همه قرمزند، از **Agent install** استفاده کنید.
- **رله‌ی Golden-GRE برای amd64 و arm64 ساخته می‌شود؛** هسته‌ی Premium نسخه‌ی amd64 است (روی arm64 از نسخه‌ی فروشنده یا شبیه‌سازی استفاده می‌شود). بقیه مستقل از معماری‌اند.
- **IPv6:** پنل دیگر IPv6 forwarding را روشن نمی‌کند (داخل تانل‌ها IPv4 است). نسخه‌های قبلی روشنش می‌کردند و با روشن بودن آن، لینوکس Router Advertisement را نادیده می‌گیرد؛ در نتیجه روی سرورهایی که مسیر پیش‌فرض IPv6 را از RA می‌گیرند، IPv6 بعد از مدتی قطع می‌شد. حالا هر بار که تانلی بالا می‌آید این مشکل خودکار رفع می‌شود. آدرس‌های سرور هم بررسی و یکدست می‌شوند و اگر IPv6 واردشده روی خود سرور نباشد، تانل با پیام واضح متوقف می‌شود.
- **چند تانل Golden-GRE روی یک سرور:** هر رله روی پورت مخصوص خودش گوش می‌دهد و یک قانون TPROXY بسته‌های پورت 53 هر سرور مقابل را به رله‌ی خودش می‌دهد؛ پس یک سرور ایران می‌تواند به چند سرور خارج Golden بزند. فقط اگر دو تانل Golden بین *همان دو سرور* بخواهید، برای دومی «DNS port» دیگری (مثلاً 5353) بگذارید.
- **فراموشی رمز / تغییر رمز از داخل سرور:** روی سرور خارج:
  ```bash
  # تنظیم رمز جدید برای ادمین:
  tunnel-panel reset-password -user admin -password "رمزجدید۸کاراکتری"
  systemctl restart tunnel-panel
  # یا پاک‌کردن همهٔ حساب‌ها تا دوباره صفحهٔ ساخت حساب بیاید (سرورها و تونل‌ها می‌مانند):
  tunnel-panel reset-password
  systemctl restart tunnel-panel
  ```
- **به‌جای `#123`** همیشه نشانی کامل گیت‌هاب را بنویسید.
- وضعیت سرویس: `systemctl status tunnel-panel` روی سرور خارج.
